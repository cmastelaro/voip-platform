# 4. Store PJSIP configuration in PostgreSQL via ODBC realtime

Date: 2026-08-06

## Status

Accepted

## Context

Endpoint provisioning defined in `pjsip.conf` requires a file edit and a reload
per change. A control-plane API built on that model would have to generate text
files and trigger reloads — workable, but it couples the backend to Asterisk's
config syntax and makes concurrent writes unsafe.

Asterisk's realtime architecture allows configuration objects to be read from a
database on demand instead.

## Decision

Store `endpoint`, `auth`, `aor` and `contact` objects in PostgreSQL, read via
Asterisk realtime. Transports remain in `pjsip.conf`.

**ODBC is mandatory, not chosen.** Asterisk ships a native PostgreSQL backend
(`res_config_pgsql`), but PJSIP configuration is resolved through the sorcery
object layer, whose realtime wizard is implemented only against
`res_config_odbc`. The resulting chain is:

``
Asterisk -> sorcery -> res_config_odbc -> unixODBC -> psqlodbc -> PostgreSQL
``

The schema is generated by Asterisk's own Alembic migrations from
`contrib/ast-db-manage`, run from a throwaway container so that migration
tooling is absent from the runtime image.

`contact` is realtime-backed for both file- and database-configured endpoints,
so live registration state is queryable with plain SQL rather than through an
Asterisk API call.

## Consequences

**Positive**

- Provisioning is an `INSERT`. The control plane needs no Asterisk-specific
  knowledge beyond the schema, and no reload is triggered.
- Registration state is a queryable table, which the admin portal reads directly.
- Enum column types enforce Asterisk's config grammar at the database level;
  invalid values are rejected on write rather than silently ignored at load.

**Negative**

- Two extra layers of indirection to debug. `realtime load ps_aors id <x>`
  queries the realtime layer directly and isolates a database/mapping fault from
  a sorcery wiring fault.
- Every lookup is a query. Acceptable at this scale; production deployments
  front this with `res_sorcery_memory_cache`.
- Sorcery section headers are keyed by the module that *registers* an object
  type, not the one that uses it. `endpoint`, `auth` and `aor` all belong to
  `[res_pjsip]`; only `contact` belongs to `[res_pjsip_registrar]`. Misfiling
  these produces a partially-resolving configuration that fails at REGISTER with
  a 500 and no clear error.
- Declaring a wizard replaces the built-in default rather than appending to it,
  so the `config` wizard must be declared explicitly to keep reading
  `pjsip.conf`.
